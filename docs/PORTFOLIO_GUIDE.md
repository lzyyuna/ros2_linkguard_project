# 作品集与面试表达

## 30 秒项目介绍

“我做了一个网络感知型 ROS 2 机器人任务系统。系统用 Topic 承载连续控制和遥测，用 Service 注入网络场景，用 Parameter 配置策略，用 Action 管理可反馈、可取消的移动任务。我为控制报文加入序号和源时间戳，实现了滑动窗口交付率、延迟、抖动、AoI和乱序检测，再用实测值驱动GOOD、DEGRADED、STOPPED、ABORTED安全状态机。命令QoS可显式切换RELIABLE/BEST_EFFORT，控制端与机器人端也可以在两个容器中跨网络通信。”

## 面试官可能追问

### 为什么网络场景切换不用 Topic？

它是低频、有明确成功/失败结果的一次性操作，Service 更合适。Topic 不保证请求者能获得直接响应。

### 为什么执行任务不用 Service？

任务持续数秒到数十秒，需要周期反馈、超时和取消。Service 不适合表达长任务生命周期。

### Parameter 和 Service 有什么边界？

Parameter 是节点配置，并带参数发现、查询和动态更新能力；Service 表达领域操作。单项阈值调节用 Parameter，原子地切换整套网络场景用 Service。

### 丢包后为什么机器人会安全停车？

robot_sim 有命令看门狗。超过指定时间收不到新指令，就将速度置零。这使安全性不依赖任务服务器能否及时发现故障。

### 应用层模拟丢包与BEST_EFFORT有什么区别？

应用层丢包由`link_emulator`随机决定是否转发，发生在ROS消息已经到达模拟器之后，
因此RELIABLE QoS不会把它补回来。BEST_EFFORT/RELIABLE描述的是DDS传输层的交付
语义，真正的QoS差异要在跨容器网络压力、限带宽或DDS故障注入实验中比较。

### 当前模拟器有什么局限？

它是二维运动学模型，没有动力学、传感器噪声和真实无线信道；双容器实验仍然运行在同一台主机上，不等同于真实无线网络。后续应增加限带宽、网络阻塞和跨主机对照实验。

## 不要这样表达

- “我会 ROS 2，因为我会发布订阅。”
- “用了 Action，所以项目很复杂。”
- “网络差时效果不好。”

要用职责边界、故障策略和量化指标表达工程能力。
